## 一、联动上次 Claude Code 对比：为什么 Gemini 跑原厂 AGY 没有出现“水土不服型膨胀”？

在本仓第二篇复盘（[满血开箱客户端终评](harness-comparison-full-default.md)）中，把第三方模型（`GLM-5.3`）接入 **Claude Code** 时暴露出了严重的**“异构客户端水土不服”**：Claude Code 带着一整套专为自家 Claude 定制的厚重系统提示词、工具使用教条与子代理引导，第三方模型塞进去后不仅每轮白背一截不适配的静态上下文，还在任务推进中反复试探空转，导致总轮数比 OMP 膨胀 **38%**，最终滚出 **`1.44×`～`2.0×`** 的 Token 账单差距。

那么把 **Gemini 4 Hydrogen** 放回它自家的 **Antigravity 官方 CLI（`agy cli`）** 与 **OMP `18.20.2`** 同台跑本套四道初级/中级工程题（详见[实验总档](../experiments/gemini-4-hydrogen-omp/README.md)），虽然官方订阅制 CLI 黑盒不暴露累计 Token 数字，但通过**动作步长（Action Steps）与成品质感**依然能做出非常清晰的横向判断：

| 对比维度（同一套 A/B/C/D 四题） | `OMP 18.20.2`（Antigravity 管线） | **Antigravity 官方 CLI（`agy cli` 原厂直连）** | 对照结论 |
|---|---|---|---|
| **客观题得分（B / C / D）** | **7/7 · 41/41 · 11/11** | **7/7 · 41/41 · 11/11**（D 题另自补 173 行回归单测） | **解题硬实力完全平手** |
| **A 题前端与算法实现细节** | 内置 `browser` 4 轮截图自检，62.5 KB | 自写脚本调临时浏览器自检（67.5 KB）；C 题手写 4 层 32 叉树 | **无明显差距，局部甚至更细致** |
| **四题累计工具/动作步长** | **172 步**（A 16 / B 56 / C 6 / D 94） | **152 步**（A 14 / B 40 / C 13 / D 85） | **步长完全同级，零空转膨胀** |
| **推理耗时水位** | 端到端总墙钟 **`25m09s`** | CLI 累计纯思考计时 **`20m17s`**（加本地命令耗时后同级） | **单会话推进效率一致** |

这组对比说明了一个核心事实：**自家模型配自家官方客户端，大脑和手脚是原厂原生对齐的。**
- Gemini 对原厂 AGY 的系统提示词与 `read_file` / `edit_file` / `run_command` 工具集高度适应，根本不会像第三方模型进 Claude Code 那样因为提示词错位而多走弯路，在初级难度题库上与极简流派的 OMP 没有拉开步长或质量差距。
- 再加上谷歌近期已通过**服务端 `FeatureProvider` 远程配置热下发**（无需更新本地二进制，对比 `1.5.4` 与 `1.5.9` 可见本地回退函数 `utils.GetCheckpointConfig` 硬编码默认值仍为 `256000`），将原厂客户端默认上下文上限从略显局促的 **`256K` 自动上调到了比较适度的 `512K`**（注：本地自定义规则单文件 `24,000` 字节、`computeTruncatedCustomizations` 总计 `20,000` tokens 的硬编码截断尚未放开），日常单会话写代码的整体可用度已经相当不错。

**既然工具适配没毛病、步长也没膨胀，为什么重度用户依然普遍反馈官方客户端“等得久、掉额度飞快”？**
顺着 `1.5.9` 二进制状态机与上万轮真实计费日志往下查，真正的病根全部指向三个纯工程基建硬伤：**不能异步执行工具、隐式 KV 缓存有效时间（TTL）太短叠加路由掉缓存，以及难堪大用的 `/compact` 压缩机制。**

## 二、硬伤一：工具状态机依然“流式假并发、执行真单步串行”

对比本仓两款客户端在 Hydrogen 实测中的工具调度方式，差异直接写在底层状态机里：

1. **OMP 的真异步并发派发**：
   核查本次 OMP 跑 Hydrogen（Antigravity 管线）全部 112 轮原始日志，有 **32 轮（占比 `28.6%`）在同一轮并发派发并并行执行了多个工具**，单轮最高 **5 个工具同时异步运行**（例如 D 题排查阶段连续 8 轮每轮并发读取 4 个源码文件）。
2. **官方 AGY（至 `1.5.9`）的严格单步串行派发**：
   反汇编 Agent 核心循环 `oneharness/internal/core.(*Machine).stepToolDispatch`（640 字节）可见，其真实调用链至今未变：
   `finishModelOutput` → `stepToolDispatch` → **`dispatchSingleToolStep`** → `resolveNextToolStepIdx`
   （二进制内虽存在名为 `executeToolCallsParallel` 的函数，但交叉引用证实它仅被安全校验套件 `policyguardian.(*Guardian).runVettingLoop` 调用，真实对话主循环从未接入）。
   反映在实际对话时间戳上就是典型的**“流式假并发、执行真串行”**：
   - 模型同轮依次吐出 `[read_file, read_file, read_file, run_command]` 时，前 3 个只需 1 毫秒的 `read_file` 明明早已生成完毕，却必须干等十几秒直到第 4 个长脚本 `run_command` 流式输出彻底结束，才开始按顺序一个接一个排队执行；同轮 5 个 `edit_file` 也是每隔 2～3 秒阶梯式串行落盘。
   - 遇到慢命令超时转后台（`WaitMsBeforeAsync` / `parkedStep`）时，工具返回值会强塞死规矩（`YOU MUST TAKE ONE OF THE FOLLOWING TWO ACTIONS...`），强迫模型要么收尾要么立刻结束当前轮干等 `<SYSTEM_MESSAGE>` 唤醒，无法边跑后台测试边自由穿插读改文件。

**单步串行是怎么传导到额度损耗上的？**
- 单纯同轮几个 `read_file` 排队串行，打包回传给下一轮的消息内容不变，虽然不直接多算一轮输入，但**白白拉长了单轮墙钟等待时间**；
- 一旦触发 `parkedStep` 后台挂起与 `<SYSTEM_MESSAGE>` 唤醒，不仅平白多费 API 轮数，实测日志中还多次抓到唤醒轮即使仅隔 `7.9` 秒也会在系统提示词边界（`~13.9k` tokens）把后续十几万历史缓存击穿作废；更重要的是，**整体变慢的节奏直接把用户推向了下一个核心大坑——极短的 KV 缓存过期窗口**。

## 三、硬伤二（账单压力总病根）：20 倍差价下的“短缓存 TTL”与瞬间路由击穿

社区近期讨论 Gemini 4 Carbon 等模型在各渠道体感额度消耗极快时，曾怀疑是“Google 在系统提示词下方反复插拔动态安全提示词（俗称‘动态甲’）破坏了 KV 缓存”。调取本地计费侧上万轮真实代码/逆向会话逐轮核对后，真相非常明确：

### 1. 先辟谣：“动态安全甲”存在，但正常写代码几乎零触发
- 公开复现脚本之所以稳定触发“动态甲”，是因为输入了特定高危精神危机/红线敏感词；服务端临时在 `systemInstruction` 正下方插入安全指令时，计费表上会留下唯一指纹——**`cacheReadTokens` 精准跌落到 `~11,000 ~ 15,000` tokens（恰好等于顶部系统提示词长度），而其后几十万历史消息全部缓存失效**。
- 但在真实高强度编程与逆向工程会话中（连续数千轮讨论源码修改、进程调试、甚至二进制补丁），这种 `~11k–15k` 部分击穿**数千轮仅偶发 1～2 次，近乎为零**，根本不是日常烧穿额度的元凶。

### 2. 真正的额度黑洞：20 倍输入差价 ×（短缓存 TTL + 节点漂移归零）

按照计价表，Gemini 4 系列（Carbon / Argon / Hydrogen）的**未缓存输入单价是缓存读取单价的整整 20 倍**（如 `$2.0/M` vs `$0.1/M`，或 `$1.50/M` vs `$0.075/M`）。在 **20 倍悬崖差价** 下，统计单模型真实长会话的缓存命中表现，问题一眼见底：

| 单模型会话样本 | 统计总轮数 | 综合缓存命中率 | 未缓存输入 (全价) | 缓存命中输入 (1/20 价) | 短间隔归零击穿 (`≤4min`) | 闲置 TTL 过期 (`>4min`) |
|---|---:|---:|---:|---:|---:|---:|
| `gemini-4-argon-b` | 1,618 | **94.8%** | 30.80M | 557.85M | 20 次 | 19 次 |
| `gemini-4-argon` | 8,002 | **93.0%** | 209.19M | 2,795.17M | 119 次 | 219 次 |
| **`gemini-4-carbon`** | 1,113 | **88.6%** | 18.57M | 144.07M | 21 次 | **50 次** |

别小看缓存命中率从 `94.8%` 掉到 `88.6%`：在 **20 倍差价**下，全价未缓存占比从 `5.2%` 翻倍到 `11.4%`，意味着**每百万上下文的平均输入扣费直接暴涨了约 `59%`**！而几乎所有伤账单的毛病，最终都汇集到了下面这两把刀上：

1. **头号硬伤：隐式 KV 缓存有效时间（TTL）太短**
   - 写代码不是无脑连发聊天——开发者看一眼改动 diff、本地跑一轮编译测试、或者切出去想几分钟架构再回来发下一句，只要停顿十几到四十分钟（实测一例仅间隔 `41` 分钟），此前攒好的 **27.5 万缓存直接过期归零**（`uncached = 286,269, cached = 0`，首字等待 TTFT 飙至 `114.7s`）。
   - 在 `gemini-4-carbon` 的 1,113 轮正常开发对话里，这种闲置 TTL 过期高达 **50 次**——**平均每聊 22 轮就要全价重算整本历史上下文一次**；而前面提到的“工具单步串行拖慢单轮耗时”，又进一步放大了踩中短 TTL 边界的概率。
2. **叠加暴击：后端负载均衡漂移导致的“几秒内瞬间 `cached = 0`”**
   - 即便一秒不停地连续自动跑工具，后端集群在实例扩缩容或流重试切节点时，一旦把请求路由到没有本地隐式缓存副本的节点，就会发生**连系统提示词都不命中的瞬间 `cached = 0`**：
     - Carbon 连续工具流中多次抓到间隔仅 `7.5s`、`12.0s`、`15.5s`、`26.4s` 就瞬间变成 `uncached = 195k~234k, cached = 0`；
     - 本仓昨天跑 Hydrogen 的 `stdout.jsonl` 同样抓到了现行（如 `D-hydrogen` 第 5 轮刚命中 `34.5k` 缓存，几秒后的第 6 轮瞬间 `cacheRead = 0, uncached = 51.5k`；`A-hydrogen-xhigh` 第 15 轮从 `100.3k` 突跌至 `5.8k`）。
   - **20 万上下文只要掉 1 次缓存，这一轮烧掉的额度就抵得上正常命中缓存连续跑 20 多轮！**
3. **`512K` 窗口扩容的双刃剑效应**：
   - 服务端把窗口放开到 `512K` 后，单会话轻松滚到 30 万～45 万上下文；平时命中缓存很爽，可一旦撞上**短 TTL 过期**或**节点漂移归零**，单刀全价重算的爆炸半径直接比 `256K` 时代翻了一倍。

## 四、硬伤三：本该帮用户省额度的 `/compact`，拆开看却有四大工程缺陷

既然长上下文撞上短 TTL 掉缓存这么肉疼，按理说最自然的解法是：**做完一个子阶段就手动敲一次 `/compact` 把历史压薄，轻装上阵**。但社区大量用户吐槽官方 `/compact` 极不好用，反汇编拆解其内部实现后可以确认，这套压缩管线不仅结构沉重，还存在至少**四大工程硬伤**：

1. **`/compact <文字>` 根本不支持自定义保留指令**：
   用户在其他主流 CLI（如 OMP / Claude Code）里习惯敲 `/compact 保留刚才查出的三个死锁条件和接口签名`，但在官方客户端里，附加的参数文字根本没被接入压缩保留逻辑，用户无法干预压缩摘要的取舍重点。
2. **提示词焊死“任务未完成”前提，结项压缩逼模型强行编造下一步**：
   内部压缩模板写死了“当前正在中途交接一个未完成任务”的叙事框架。如果你在某个功能已经顺利收工、准备在同一会话开启下一个相关小需求前敲 `/compact`，模型会被模板硬逼着无中生有编造一堆“尚未完成的下一步计划”，污染后续上下文。
3. **新版 `RESUME RULES` 矫枉过正，自缚手脚**：
   为了省压缩后的动作，新版恢复规则往上下文里塞入了极其僵硬的禁令——**禁止重读此前已读过的文件、禁止运行 `git diff`、单次读取硬限 `100` 行、禁止主动排查边缘情况（edge cases）**。这等于强迫模型把有损压缩摘要当成“绝对无误的圣旨”；一旦摘要漏掉一行关键状态，模型既不能重看原文件也不能跑 `git diff` 核对，直接变成蒙眼修 Bug。
4. **刚补完一串底层失血旧伤**：
   这套重型压缩逻辑此前长期带着压丢用户附件、压丢子代理任务上下文，甚至在发起压缩请求时**漏带工具声明（Tool Declarations）导致自己主动把前缀 KV 缓存捅破**的旧伤，直到近期版本才刚把这几个低级漏洞补上。

## 五、总结

把这四篇实验与底层拆解串起来，对 **Gemini × Antigravity 官方客户端** 的评价可以浓缩为非常公允的三句话：

1. **选道建议明确**：远离高危封号的反代链路，老老实实用官方原厂客户端；
2. **模型与原厂工具适配合格**：不同于第三方模型硬塞 Claude Code 时的水土不服与步长膨胀，Gemini 在自家 AGY 里的动作步长、代码质量与 OMP 完全同级，配合刚放开的 **`512K`** 默认上下文，基础干活体验是稳健可用的；
3. **真正的改进靶心全在基建**：只要谷歌后续能把 **① 延长隐式 KV 缓存 TTL 并修复节点漂移掉缓存**、**② 状态机打通工具真异步并发执行**、**③ 重做支持自定义指令且不自缚手脚的轻量 `/compact`** 这三个工程坑填平，原厂客户端压在重度用户头上的“慢”与“烧额度”两座大山就能迎刃而解。
