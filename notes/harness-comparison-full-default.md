# Harness 横向复盘（二）：满血开箱重测后的客户端终评与选型结论

> **前情与数据底座**：在 [第一篇复盘（精简六工具口径）](harness-comparison-minimal-tools.md) 里，我们发现前任测试脚本为了“控制变量”，把 OMP 和 Claude Code 自带的看家工具全给阉了。补立[满血开箱规矩](../README.md#客户端实测规矩满血开箱)并跑完 [`GLM-5.3（满血开箱）`](../experiments/glm-5.3-full-harness/README.md) 两轮共 18 场（16 场首跑 + 2 场封堵 `read(URL)` 后的独立补测）之后，加上此前的 32 场 GLM 实验与 DeepSeek 实验，仓库累计已有 **50+ 场带完整 Token 与工具流记录的对照样本**。这篇直接回答核心问题：**在挂载国产/第三方主力模型日常干活时，Claude Code 和 OMP 到底谁更好用、差在哪？**

---

## 一、先给总评：在已实测模型上 OMP 综合胜出——更容易激活内置工具，且不背空转工具税

如果把两套客户端放在**“接智谱 `GLM-5.3` 这类第三方旗舰模型开箱干活”**的真实场景下打分，满血重测后的胜负关系比精简工具阶段清晰得多：

1. **OMP 放开原生工具后拿到了实打实的工程闭环增益，且账单依然便宜三成以上**
   - 满血独立 8 场合计，OMP 墙钟 **`50m04s`**、折算等价输入 **`1.76M` tokens**；Claude Code 墙钟 **`62m55s`（`1.26×`）**、折算等价输入 **`2.54M` tokens（`1.44×`）**，其中缓存读取更是高达 OMP 的 **`1.60×`**（`7.40M` vs `4.62M`）。
   - 第一阶段里 OMP 暴露的两个明显短板——**A 题盲写纯静态无脚本 SVG**、**C 题偶发漏跑大数据压测**——在放开内置 `eval`（持久化 Python/JS 内核 + 无头 Chromium `browser`）之后**当场消失**：两轮 A 题它全都自己拉起无头浏览器查报错、甚至隔帧采样曲柄旋转矩阵确认动画真在动；C 题直接在内核里写暴力对拍，两轮 `1m13s–1m44s` 全满 `41/41`。
2. **Claude Code 放开全套默认工具后，在这批任务上只涨了静态底噪、未触发额外能力**
   - 放开限制后，Claude Code 向模型暴露了 `Agent`（含 `Explore` 子代理）、`EnterWorktree`、`Workflow`、`NotebookEdit`、`Monitor`、`ScheduleWakeup` 等 24 个工具定义，首轮静态输入从精简模式的 `~14k` 涨到了 **`~19.0k` tokens**（对比满血 OMP 首轮仅 **`~8.3k` tokens**）。
   - 然而在全部场次中，**`GLM-5.3` 调用 `Agent` 子代理的次数是 `0`**（OMP 侧 `task` 子代理同样是 `0`）。多出来的上万 token 工具定义在每一轮对话里跟着 `cache_read` 反复计费复读（8 场缓存读取从精简版的 `4.64M` 暴涨到 **`7.40M`**，涨幅 **+60%**），却没有换来任何一次子代理上下文隔离。

## 二、为什么会出现这种不对称？核心在于“按需懒加载 + 明文工作流触发” vs “全量平铺工具 Schema”

从全部日志的工具调用轨迹看，两边拉开差距的真实原因不是哪个工具多，而是**工具怎么塞进上下文、靠什么指令触发**：

| 架构维度 | Claude Code `2.1.322` | OMP `18.18.8` | 实测观察到的直接后果 |
|---|---|---|---|
| **工具文档装载方式** | 启动即全量平铺 24 个工具 Schema（首轮约 `19.0k` tok） | 核心工具精简（首轮约 `8.3k` tok），LSP / AST / Browser 详细文档走 `xd://` 按需读取 | 没用到的工具在 OMP 里几乎零成本；在 Claude Code 里每轮固定多背约 `11k` tok 缓存底噪，50 轮 D 题单这一项就多滚出 `500k+` 缓存输入 |
| **高阶工具激活机制** | 把 `Agent`、`Workflow`、`EnterWorktree` 等摆进工具列表，是否调用留给模型自由裁量 | 系统提示词对关键场景写死强制动作（例如明文规定 Web UI 必须调 `browser.open` 做视觉验证） | 明文规则直接激活了 OMP 的 `eval` + `browser`（A 题 2/2 触发、C 题对拍触发）；而两边留给自由裁量的子代理（`Agent` / `task`）在这批单点题上触发率双双为 `0` |
| **前端视觉验收能力** | 原生不含内置无头浏览器（需额外配置外部 MCP） | `eval` 原生内嵌无头 Chromium `browser` | OMP 开箱就能自己跑完“写页面 → 渲染查错/抽样动画帧”闭环；Claude 只能盲写（导致 `r2/A-claude` 窄屏控件遮挡而不自知） |
| **代码编辑协议** | `Edit` 全文精确字符串替换（`old_string` → `new_string`） | 行号 + 4 位快照哈希锚点（`[file#TAG] PUT N.=M:`） | 改大文件或缩进敏感块时，OMP 不需要把大段原代码在 Output Tokens 里原样复述一遍，既省输出耗时又降低缩进匹配失败率 |
| **文件读取能力边界** | `Read` 仅限本地文件，抓网页走独立的 `WebFetch` | `read` 统一接管本地文件、压缩包、SQLite、二进制反编译与静态网页 URL | 日常干活时 OMP 读文档/看源码包极顺手；但做闭卷评测时，`read(URL)` 是极易漏防的联网旁路 |

一句话概括本轮实测能证伪和证实的事：**把一堆高阶工具平铺进 Schema 并不会让模型自动变强，没触发时反而全是每轮复读的负资产；反而是“平时懒加载省底噪 + 遇到对应题型靠系统提示词明文推一把”的设计，工具激活率更高、账单也更轻。**

## 三、修正第一篇的两个旧判断：在准确率与稳定性上，真实边界在哪？

对比精简版与满血版两档数据，第一篇复盘里有两条结论需要更新：

### 1. A 题（开放前端生成）：从“Claude 兜底更好”反转为“OMP 交付更稳更快”
- **旧判断（精简版）**：OMP 收敛太快，经常交几 KB 的无脚本静态 SVG 草草了事；Claude 每次都肯花十几分钟写完整 JS 动画，兜底更强。
- **新结论（满血版）**：之前 OMP 交静态 SVG 是因为内置 `browser` 被阉了。满血状态下，OMP 两轮都在 **4 分钟出头**交出了带完整 JS 骑行动画、双视口零裁切零报错的成品，还自己跑了帧采样验证；Claude 花了 **7 分钟左右**、吐了近两倍代码，虽然交互点子更多（第二轮主动加了暂停键和倍速滑块），但因为没法开浏览器看一眼，窄屏下浮层直接挡住了太阳和车轮下缘。**在前端任务上，有没有内置浏览器闭环，比系统提示词啰不啰嗦重要得多。**

### 2. B / D 题（存量工程修 Bug）：Claude Code 的“谨慎慢热”确实在防御性细节上略占小便宜，但治标不治本是模型通病
- **旧判断（精简版）**：只有 Claude 会在 B 题翻车（Flash `3/7`），OMP 在 B 题稳如泰山。
- **新结论（满血版）**：把 `read(URL)` 封死后，OMP 在 `r2/B-omp-retry` 跑出了 **`5/7`**——花了整整 44 轮把 `method` 和 `body` 修得滴水不漏，却忘了 `prepared_request = req.copy()` 还会让第一跳跨主机剥掉的 `Authorization` 头在第二跳复活；反观 Claude 本档两轮 B 题都干净利落地写出了 `req = prepared_request`（`7/7`）。
- 再加上 D 题四场独立运行虽同为 `10/11`，但在事后“测试与 `tearDown` 双重抛错”诊断中，满血 Claude 两轮都顺手包了 `try/finally`（`2/2`），满血 OMP 是一有一无（`1/2`）。
- **客观评价**：这说明**“钻进局部症状漏掉全局根因”是模型采样方差的共性问题，哪个 Harness 都免疫不了**；但 Claude Code 偏详尽保守的系统提示词，确实让模型在修老代码时更倾向多包一层 `try/finally` 或多看一眼上下文，代价就是多付 `44%` 的 Token 和 `26%` 的等待时间。

## 四、最终实战选型建议

基于 50+ 场实测账单与交付物质量，按真实使用场景给出直接结论：

| 你的实际场景 | 推荐 Harness | 理由与搭配建议 |
|---|---|---|
| **已实测主力模型**（`GLM-5.3`、`DeepSeek V4.1 Flash`）做日常研发、前端、算法与脚本 | **OMP（首选）** | 实测省约 **30%–50%** 计费 Token、快 **20%–40%**；`xd://` 懒加载不撑爆缓存；系统提示词更容易激活内置 `eval` + 无头 `browser` 形成视觉与对拍闭环。涉及复杂老仓库修 Bug 时，随口补一句“改完检查异常清理与状态跨跳残留”即可补齐防御细节。 |
| **已实测轻量模型**（`GLM-5.3-Flash`） | **OMP（强烈建议）** | 轻量模型在 Claude Code 里极易陷入 50–70 轮长线空转，缓存复读雪球实测让成本翻到 **1.9×–2.0×**，而得分并无稳定优势。 |
| **未实测留白**：Anthropic 原生模型（Opus / Sonnet）或跨几十模块的大型工程题 | **尚无实测数据，不下结论** | 本仓目前只测了国产/第三方模型与单点题，不能凭猜测断言换上 A 家自家模型后 Claude Code 就能扳回工具税、更不能断言 OMP 会输——留待后续真跑数据说话。 |
