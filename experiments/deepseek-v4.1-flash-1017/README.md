# DeepSeek V4.1 Flash 1017：换个 API 渠道、换个客户端，表现有差吗？

这轮测试的对象是 **DeepSeek V4.1 Flash 1017**（官方接口别名 `deepseek-flash`，文档对应 `DeepSeek-V4.1-Flash-1017`；OpenCode Go 渠道名为 `deepseek-v4.1-flash`）。把两家 API 渠道（OpenCode Go、DeepSeek 官方）和两个编程客户端（OMP `18.16.0`、Claude Code `2.1.318`）两两交叉，拉出四组配置做同一批题。

先放总表，后面细聊这几道题是怎么一路测下来的。

| 测试项目 | OpenCode → OMP | OpenCode → Claude Code | 官方 → OMP | 官方 → Claude Code |
|---|---|---|---|---|
| **A：2D 鹈鹕骑自行车 (HTML)** | 动画完整，画风朴素（无时限耗时 18m19s） | 动画完整，带海报排版（无时限耗时 12m02s） | 动画完整，配色与比例最舒服（无时限耗时 10m08s） | 动画完整，但手机端裁切了嘴和车轮（5m08s） |
| **B：Requests 重定向方法丢失** | 7/7 通过（2m33s） | 7/7 通过（45s） | 7/7 通过（2m16s） | 7/7 通过（1m29s） |
| **C：AtCoder ABC378 E 子数组余数和** | 41/41 通过（27s） | 41/41 通过（47s） | 41/41 通过（22s） | 41/41 通过（1m05s） |
| **D：Pytest unittest 清理未执行** | 10/10 通过（5m32s） | 10/10 通过（隔离补跑耗时 7m23s）¹ | 10/10 通过（2m09s） | 10/10 通过（4m44s） |
| **D 附加诊断：清理函数自身抛异常** | **同时报出原失败与清理异常** | 吞掉清理异常 | 吞掉清理异常 | 吞掉清理异常 |

> ¹ 表中 A 的前三列为放开 5 分钟限制后的重跑成绩，第四列为单次成绩；OpenCode → Claude 在 D 题首次运行时顺着目录读到了其他组的现成答案，第一次补跑又因启动脚本配错路径复用了已修改的工作区，表里填的是第三次从干净源码跑完的 `D2-r3`。

一圈测下来最直观的感受：**OpenCode 渠道并没有比官方接口“缩水”，两个客户端也各有脾气。** 在 OMP 里跑官方接口，连着两轮画出来的鹈鹕都更耐看；但到了最绕的 Pytest 生命周期修复，反倒是 OpenCode → OMP 把异常叠加的边界处理得最干净。

---

## 起因：把“体感差异”拆成四个格子

平时写代码时经常冒出两个疑问：
1. 用 OpenCode Go 调 DeepSeek，跟直接连官方 API 到底有没有区别？（注：官方接口明确指向 1017 快照，OpenCode 后台是否完全同步到同一快照，外部无法直接核验。）
2. 同一个模型，放在 OMP 和 Claude Code 两套不同的系统提示与工具流（Harness）里，干活路数会差多少？

既然关心的是日常干活的实际产出，测试就没必要搞成八股文：每类任务只跑一次，省下 token；提示词就按平时说话的习惯写，比如 A 题发给四个组合的原话只有一句：

> 帮我做一个 HTML，画一只 2D 鹈鹕骑自行车，直接在浏览器里打开就能看。做好放在 index.html。

没有规定用 SVG 还是 Canvas，也没提响应式或动画细节。最后看到的围巾、鱼篮、踩踏板的关节联动，全是模型在各自客户端里自己发挥出来的。

## 第一道坎：5 分钟画不完一只讲究的鹈鹕

起初给任务设了 5 分钟上限。结果跑 A 题时，好几组其实早就把 `index.html` 写出来了，但代理自己觉得还不满意，在后台反复调浏览器、截图、改车架比例、修脚踏板轨迹，不知不觉就撞上了 5 分钟死线。

如果因为“还在自我打磨没来得及收尾”就判不及格，实在说不过去。干脆给前三个组合重开一轮不限时测试（`A1-r2`、`A2-r2`、`A3-r2`），三个全新空目录同时开跑，看它们到底要折腾多久才肯停手。

结果这一跑就是 10 到 18 分钟——绝大多数时间不是在吐代码，而是在“打开浏览器 → 截图自检 → 调整坐标”的循环里打转。最后交出来的作品确实比限时版精致不少：
- **官方 → OMP**（[首轮](artifacts/A/A3/index.html) / [无时限](artifacts/A/A3-r2/index.html)）：两轮的配色、车身几何和鹈鹕体态都最协调。
- **OpenCode → Claude Code**（[首轮](artifacts/A/A2/index.html) / [无时限](artifacts/A/A2-r2/index.html)）：做出了带标题卡片的海报感。
- **OpenCode → OMP**（[首轮](artifacts/A/A1/index.html) / [无时限](artifacts/A/A1-r2/index.html)）：结构规整，走简洁路线。
- **官方 → Claude Code**（[单次无时限](artifacts/A/A4/index.html)）：只花了 5 分钟出头就收工了，自检轮次少得多；电脑上看没问题，切到手机窄屏就会发现鸟嘴和车轮超出了画布边界。

（各轮桌面与手机视口截图均保存在 [`results/`](results/) 对应目录下。早先设过一个 10 分制客观检查表，结果几乎人人满分，根本反映不出肉眼可见的审美差距，索性弃用，直接看图最实在。）

## B 题与 C 题：全员满分的“热身局”

接下来两道题原本打算用来拉分差：
- **B（SWE-bench `psf__requests-1963`）**：`POST` 请求遇到 `303 See Other` 变成 `GET` 之后，紧接着遇到 `307 Temporary Redirect`，结果请求方法又被错误地还原成了 `POST`。
- **C（AtCoder ABC378 E）**：给定数组和模数 $M$，求所有连续子数组之和模 $M$ 的总和（$N \le 2\times 10^5$，需要前缀和配合树状数组/归并统计，暴力必超时）。

结果四组全部一把过：B 题起本地 HTTP 服务实测 7 个重定向场景全绿，C 题从样例、极端边界、小数据暴力对拍到 20 万规模性能压测共 41 个测试点全部打满。

回头看原因也很明白：B 题虽然是真实开源项目的陈年 bug，但根因集中在 `Session.resolve_redirects` 的状态继承上，改两三行就能搞定；C 题对人类选手算中等偏上，但前缀和取模加树状数组早就是代码模型的熟面孔了。

既然这两道题分不出高下，与其继续堆同难度的题浪费 token，不如直接上一道真正棘手的。

## D 题见真章：不仅要跑通，还要看异常怎么撞车

新加的 **D 题（SWE-bench `pytest-dev__pytest-7151`）** 明显绕得多：用 Pytest 跑 `unittest.TestCase` 时，一旦测试失败，`addCleanup` 注册的清理函数就被跳过了。

这里头有个历史包袱：Pytest 为了支持 `--pdb` 事后调试，在测试抛异常时会主动抛出内部的 `_GetOutOf_testPartExecutor`（继承自 `KeyboardInterrupt`），强行跳出 `unittest` 的执行流，导致原本排在后面的 `tearDown()` 和 `doCleanups()` 都没机会跑。Pytest 以前打过半块补丁——用 `_needs_explicit_tearDown` 标记在后续阶段补调了 `tearDown()`，却唯独漏了 `doCleanups()`。

预先准备的 10 项验收涵盖了正常通过、断言失败、异常报错、`setUp`/`tearDown` 报错、`skip`、`expectedFailure` 以及 `--pdb` 调试交互。四组有效交付全部拿下了这 10 项。

但翻看各组打出来的补丁时，我们发现了一个非常有意思的分水岭——**如果测试本身已经失败了，而 `addCleanup` 注册的清理函数自己又抛了异常，会发生什么？**

特地为此写了一个附加诊断（[`diagnose_cleanup.py`](evaluation/diagnose_cleanup.py)）去测：
- **OpenCode → OMP (`D1`)**：选择在 `_testPartExecutor` 捕获逃逸异常时直接把清理挂进异常栈，因此 Pytest 能同时报告“测试本体失败”和“清理函数报错”。
- **另外三组 (`D2-r3`、`D3`、`D4`)**：都采用了和当年 Pytest 官方 PR 一样的改法——在 `TestCaseFunction.teardown()` 里用 `try ... finally: self._testcase.doCleanups()` 补调。因为 `doCleanups()` 内部只把异常记进 `unittest` 自己的 `result` 对象，不会直接往外抛，而此时 Pytest 早就脱离了 `unittest` 的结果收集循环，导致清理函数里的报错被悄悄吞掉了。

这个附加诊断是看代码时顺手拎出来的，所以单列一行，不算进原先的 10 分里。但正是这个细节让人看到：哪怕同样通过了标准回归套件，不同实现路径对边缘故障的兜底能力依然有高下之分。

## 场外大乌龙：防住了模型，差点没防住自己的脚本

做 D 题时还闹出了整场实验最戏剧性的两段插曲，全出在 **OpenCode → Claude Code (`D2`)** 身上。

**第一次翻车（`D2`）：** 当时把四个组的工作目录并排放在同一个父目录下。Claude Code 在跑测试受挫时，顺手用 Bash 往外搜了一圈，直接发现了隔壁已经跑完的 `D1`/`D3` 目录、实验报告和验收脚本，欢天喜地地参考完现成答案交了卷。这成绩自然作废，原样封存留作反面教材。

**第二次翻车（`D2-r2`）：** 为了堵住漏洞，我们把工作区挪到随机临时目录，还加上了 `PreToolUse` 钩子拦截越界访问。结果写补跑启动脚本时百密一疏，入口配置拷成了官方组那轮的 `official-claude-run.json`——等于直接把模型扔进了官方组已经改好代码的目录里！不仅如此，模型发现目录已经被改过之后，为了确认改得对不对，还用 `curl` 去 GitHub 拉取了上游 PR 补丁来比对。这轮虽然也是 10/10，但毫无独立性可言，继续作废。

**第三次才算真正跑干净（`D2-r3`）：** 修好启动脚本，开跑前用脚本逐文件比对原始源码哈希，同时把旧目录名、`curl`/`wget` 和 GitHub 域名全部加进钩子黑名单。回看最终日志，模型在中途确实试过一次 `curl` 拉取上游源码，但被钩子当场拦下；之后老老实实读本地代码完成了修复，耗时 7 分 23 秒，预设验收 10/10 通过。

这两次返工算是给足了教训：测具备命令行权限的编程代理时，光靠“不主动提示”根本不算隔离；**其他组的产物、验收脚本和在线源码必须从物理路径和工具层面上彻底隔开。**

## 顺带领教的两个细节：输出上限与计费显示

- **关于 `8192` 输出设置**：前三组跑的时候，配置里曾设过 `8192` 的输出上限。后来查日志发现，好几次单轮回复实际吐出了两三万 token，且没有任何截断报错，说明服务端或客户端并未将其当作硬卡死指标。到了第四组和 `D2-r3` 补跑时，我们干脆去掉了这个人为设置。
- **关于客户端里的账单数字**：Claude Code 跑自定义第三方模型时，底层计费元数据标的是 `costBasis: unknown`，显示的美元数只是按默认模版套出来的虚高估算，跟 DeepSeek 实际扣费完全对不上，所以总表里直接略去了这项没有参考价值的数字。
