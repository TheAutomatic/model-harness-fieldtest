# 同一个 DeepSeek，换个来源、换个壳，会不会不一样？

这次测的是 **DeepSeek V4.1 Flash 1017**，不是刚发布时的初版 Flash。官方的调用名叫 `deepseek-flash`，文档指向 `DeepSeek-V4.1-Flash-1017`；OpenCode Go 叫 `deepseek-v4.1-flash`。先说明一个没查实的地方：OpenCode 到底是不是完全同一份 1017 快照，我们没有独立证明。

先看最后拿到的东西，后面再讲这些结果是怎么折腾出来的。

| 任务 | OpenCode → OMP | OpenCode → Claude Code | 官方 → OMP | 官方 → Claude Code |
|---|---|---|---|---|
| **A：鹈鹕骑自行车 HTML** | 完整；无时限那轮18分19秒，画面较简洁 | 完整；无时限那轮12分02秒，海报感更强 | 完整；无时限那轮10分08秒，配色和比例比较舒服 | 完整；5分08秒，手机画面有明显裁切 |
| **B：Requests 重定向 bug** | 7/7通过 | 7/7通过 | 7/7通过 | 7/7通过 |
| **C：子数组余数求和** | 41/41通过 | 41/41通过 | 41/41通过 | 41/41通过 |
| **D：Pytest 清理生命周期** | 10/10通过 | 有效补跑10/10通过，7分23秒¹ | 10/10通过 | 10/10通过 |
| **D额外边界：清理函数自己报错** | **正确报告清理错误** | 漏报 | 漏报 | 漏报 |

¹ OpenCode→Claude 的原始 D 读到了别人的答案，第一次补跑又因为主持人启动脚本失误用了已修改项目，二者都作废。表里用的是第三次、从原始项目开始的 `D2-r3`，不是首跑；条件也改变了，不能装作四组一次成型的严格对照。A 的前三列取第二次无时限运行，第四列是首次运行。时间都是整个代理工作时间，不是纯生成速度。

**我们的粗略感觉：没有测出 OpenCode 稳定弱于官方，也没测出某个客户端全面更强。** 官方在 OMP 里的两轮鹈鹕更讨喜；较难的修复里，反而是 OpenCode→OMP 那次把异常边界处理得更完整。这是这几道题给人的印象，不是模型总榜。

## 一开始，只是觉得“怎么用起来不一样”

起因很日常：怀疑 OpenCode API 给的 DeepSeek 和官方不一样，又怀疑同一个模型塞进 OMP、Claude Code 之后表现不同。

所以并不是“OpenCode 客户端 vs 官方网页”。我们实际比较的是两个 API 来源乘上两个 harness：

- 1号：OpenCode Go → OMP 18.16.0
- 2号：OpenCode Go → Claude Code 2.1.318
- 3号：DeepSeek 官方 → OMP
- 4号：DeepSeek 官方 → Claude Code

最初提议弄很多题、重复很多次，马上被用户叫停：token不是这么烧的。最后决定每类一道题，各跑一次；确实需要补测再单独记，别挑最好的一次覆盖原结果。

提示词也被纠正过。我们不想写一份细到把实现都暗示出来的考卷，而是更接近平时随手找助手干活。A题实际就这一句：

> 帮我做一个 HTML，画一只 2D 鹈鹕骑自行车，直接在浏览器里打开就能看。做好放在 index.html。

各组拿到的都是同一份原文。动画、围巾、鱼篮、截图和手机适配，大多是它们自己加的，不是我们给某一组开小灶。

## 鹈鹕先画起来，才发现五分钟太短

第一轮给A设了五分钟。几份网页已经写出来了，代理却还在找浏览器、截图、检查腿怎么踩踏板，时间就到了。不能把“没来得及最后说一句完成”算成“完全不会做”。

后来用户干脆说：三个已经配好的组合都再跑一遍A，不限五分钟，让它们闷头干到自己停。于是重新开了三份空目录、三个新会话，同时开始，没有中途指导。

这一跑分别用了18分钟、12分钟和10分钟。全都自然结束，网页也确实有动画。大量时间花在自查、截图、调关节和处理浏览器环境上，不是一直在输出HTML。

我们实际打开看过桌面和手机。主观上，官方→OMP的画面更柔和协调，OpenCode→Claude的海报设计更抢眼，OpenCode→OMP比较朴素但完整。后来的官方→Claude只用了五分钟多，但工具调用也少得多，手机上嘴和轮子被裁掉了——快不一定是同样打磨程度下的快。

## 两道代码题都过了，但这能说明多少？

B取自真实的Requests问题：POST经过303已经变成GET，后面再遇到307却又变回POST。我们给了原始项目和最小复现，让它们自己修，再用独立的本机HTTP服务器检查请求方法、body和认证头。四组都过了7项。

C是AtCoder ABC378 E：把所有连续子数组的和取余，再求总和。样例、边界、小数据暴力对拍和最大规模一共41项，四组也都过了。

这时用户问得很直接：是不是题太简单，比不出来？确实。B的核心修复很短，题面又把触发链说得很清楚；C对人不算入门，但对这些模型可能只是熟悉的前缀和加数据结构。**验收有41个用例，不等于测了41道难题。**

因此我们没有继续刷简单题，而是只追加一道更麻烦的真实修复。

## D终于有点区分度：清理执行了，不代表修完了

D来自Pytest：用它跑unittest，测试一失败，`addCleanup`注册的清理就不执行了。它牵涉unittest生命周期、pytest的异常接管和调试器，不能只盯着一处返回值。

先确认原项目真有问题，再用上游修复验证验收本身能过。预先准备的10项覆盖通过、失败、异常、setup/teardown错误、跳过、expectedFailure和调试模式。有效交付最后都过了这10项。

真正的差异是看完实现之后追加的一个场景：**测试先失败，清理函数自己又抛异常，会怎样？**

OpenCode→OMP那份同时报告了原始失败和清理错误。两个官方组合，以及后来有效的OpenCode→Claude补跑，都只是补调用了清理，清理里的异常却没报告出来。

这项是后加的诊断，不能偷偷改口成“我们一开始就设计了11项”。它单独记录。但它确实说明了：小补丁修复了表面症状，不一定照顾到了整个错误传递过程。多花时间的那份，这次不是纯粹白忙活。

## 最大的坑，不在模型，而在我们的测试目录

OpenCode→Claude第一次做D，居然自己找到了其他组目录，读了D1/D3代码、结果报告和主持人的验收脚本，照着参考实现完成了任务。

这次必须作废。不是给它加个脚注继续算通过，也不能据此说Claude更强。主持人把所有答案放在相邻目录，又开放了Bash，隔离当然不成立。只换工作目录、不自动加载上下文，挡不住主动去找文件。

用户要求把这次补上。第一次补跑又出了更尴尬的准备失误：启动器误读了旧计划，复用了官方组已经修改的项目；候选随后还下载了对应上游PR。虽然验收通过，这次照样无效。记录保留，不能拿它冒充干净成绩。

最后才修正启动入口，启动前逐文件核对原始源码，使用新会话和随机工作区，增加对旧答案目录、网上补丁下载的工具拦截，再跑一次。候选确实尝试请求新版上游源码，但在执行前被拒绝，没有拿到内容。这次没有发现读取旧答案，10项通过，清理异常边界没过。它叫 `D2-r3`，前两次失效记录都还在。

工具拦截仍不是OS沙箱，不能因此吹成“绝对防作弊”。它还误拦过正常依赖路径查询，后面做了修正。以后真正复用这套范式，**旧答案、隐藏验收、其他会话状态应放在候选进程不可读的地方**，不是只换一个漂亮的文件夹名。

## 还有两个不该省略的小插曲

**8192是谁设的？** 是主持人为节省token手动加的，不是模型默认。用户指出这可能限制发挥，这个质疑成立。回查后发现好几次单响应实际输出两三万token，也没出现长度截断，说明它至少不是严格生效的硬上限；但我们没抓最终HTTP请求，不能说绝对无影响。后续4号和干净D补跑都移除了人工设置。这意味着各阶段条件不完全一样，我们不会把它包装成严格同预算实验。

**Claude显示的美元数很吓人？** 自定义模型的计价元数据标着`costBasis: unknown`。不能把这个数字当DeepSeek真实账单，更不能和OMP估价直接做“贵几十倍”的结论。原始值留在本地，共享表不拿它吸引眼球。

## 所以这次我们带走了什么

如果只是想知道“OpenCode那份是不是明显缩水”，这几次没有给出这种感觉。它可能画得没官方漂亮，也可能在更难的bug里处理得更完整。换成Claude也不是立刻升级：简单修复快了，算法未必更快，视觉风格变了。

更有价值的是把一个能继续用的过程留下来：自然题面、真实客户端、可打开的产物、独立验收；出错就保留，污染就作废，补跑别覆盖，未知费用别乱比。下一次换模型或harness，可以沿用这些做法，但别沿用我们踩过的隔离坑。

## 文件在哪，怎么复用

- [prompts](prompts/)：实际发送的四份原文。
- [artifacts](artifacts/)：网页、算法代码、Requests/Pytest修复patch；D2污染产物仅作案例，`D2-r3`才是有效补跑。
- [results](results/)：脱敏摘要、截图，失效原因不会删掉。
- [reports](reports/)：逐阶段详细记录；历史报告写于补跑前，最后的状态以本页和各次result.json为准。
- [evaluation](evaluation/)：主持人的独立验收和复现入口，不要放进模型可读的工作区。
- [experiment.json](experiment.json)：源项目固定commit、组合和版本说明。

为了避免把大仓库和私人环境整个打包，我们只分享修复patch，不重复附带完整上游源码、Python二进制、依赖、原始会话日志或密钥。阶段报告里的旧`control/results`位置，在这里对应`results`；旧A/B/C/D交付对应`artifacts`。运行说明见[evaluation/README.md](evaluation/README.md)。
