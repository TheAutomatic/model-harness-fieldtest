# OMP × 两个 DeepSeek 来源：首轮结果

仅运行 OMP。OpenCode Go 为 1 号，官方为 3 号。Claude Code 的 2/4 号未启动。每题每组只跑一次，无补测。

## 结论

本轮没有观察到 OpenCode 来源在编程正确性上明显弱于官方：同一道真实 bug 两边均通过 7/7 独立验收，算法题两边均通过 41/41 本地验收。鹈鹕页面两边均可打开，官方的装饰细节更多；OpenCode 的进程触及时限，但留下了可用页面。不能由三题一次的试用证明能力相同，也不能证明底层模型快照相同。

## 验收证据

A：主持人实际用 Edge 打开两个本地 HTML，固定真实视口 1000×700、deviceScaleFactor=1。两份均无观察到的页面错误或裁切。A1 是简洁道路/天空插画；A3 是更丰富的海边明信片设计。两份均能看出鹈鹕、车架、两轮和骑乘关系，粗评分量表已饱和。评分时主持人知道路径，因此并非盲评，不将这个主观分数当作显著优劣证据。

B：提交结束后逐个使用本机 HTTP 服务器，验证 303/302/301 后再 307 的请求方法，以及 body、HEAD、GET、跨 host 认证头。两边均通过。两份都采用连续使用上次 prepared_request 的修复方向；B1 在发送后更新，B3 在发送前更新。B1 同时修改项目测试与变更记录，B3 修改变更记录；验收使用主持人自己的独立程序，不以候选自己改过的测试判定。

C：逐个执行两个官方样例、5 个边界例、32 个固定种子小数据暴力对拍和2个最大规模例，共41项。每例15秒上限。两份均全通过；此为本地验收，不是 AtCoder 官方提交 AC。

## 控制与限制

- OMP 18.16.0，high 档位；正式消息日志确认 1 号实际模型为 opencode-go/deepseek-v4.1-flash，3 号为 deepseek/deepseek-flash。未出现 Sol 或其他模型代答。用于 A 批的两个外层启动工人只运行命令，没有接收题面或编写交付。
- 同题提示词逐字相同，哈希与冻结记录一致。A 两组启动差 3.022 秒，B/C 使用同一启动器屏障，时间差低于 1 毫秒。
- 六个独立 OMP 状态目录、新会话、不复用前题上下文；关闭额外 skills、规则、上下文文件、扩展、LSP、标题生成、预走、缓存预热、额外子代理和搜索工具。
- 开放本地 read/bash/edit/write/grep/glob。两边用相同工具集，允许自行验证；没有主持人追问或提供错误定位。
- maxTokens 注册为 8192/响应；多轮总输出可超过8192，服务端上限行为未做独立抓包验证。
- 未使用 OS 沙箱。文件工具限制 control/prompts，但 shell 理论上仍可访问主机/网络；不宣称隐藏评测具备安全隔离。
- 两边都标称 V4.1 Flash；官方文档指向 V4.1-Flash-1017，OpenCode 精确快照是否相同仍未证实。
- 固定公开老题可能被训练见过；只适合低成本选型观察，不构成统计结论。

## 追加 D：Pytest 清理生命周期修复

用户授权再追加一道更难修 bug 题，两来源各一次，仍未启动 Claude。来自 SWE-bench 完整集 pytest-dev__pytest-7151，固定源码、自然题面，独立新会话。计划见 D-PLAN.md。原始项目因断言失败/异常/调试失败漏清理，预设验收7/10，上游修复10/10。

|---|---|---|

最后一项是阅读两份实现后追加的诊断，不属于预先冻结的10项，不把正式成绩改写成11项。两个候选均已结束，未反馈失败原因、未补测或修改候选答案。

诊断实际输出：D1 为 `1 failed, 1 error`，包含 `cleanup sentinel error`；D3 为 `1 failed`，没有该清理错误。两者都保留原始断言失败。场景与清理生命周期直接相关，不是按实现文本或补丁形式打分。

因此本题不能简单说“官方更快，所以更强”：官方修得更快且补丁较小，但一个相关异常报告边界不完整；OpenCode 花了更久，执行流程调整较全面，覆盖了这个边界。这是一次样本中的真实质量差异，不证明任一来源普遍更强。

产物：D/D1、D/D3；完整记录在 control/results/D1、D3。verification.json 为预设10项，cleanup-error-diagnostic.json 为明确标记的事后诊断。原三题记录保持不变。
